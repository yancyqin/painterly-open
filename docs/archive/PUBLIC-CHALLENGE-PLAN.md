# 公开挑战、账户与艺术房间计划

> **已归档 2026-07-20** — Explore/Lobby、举报/审核、账户 OTP、entitlement 全部建成;三项技术闸门完成。尚未完成的扩大曝光前事项(异常图像检查、儿童 UGC 供应商审查)已并入 ../COMPLIANCE.md。

## 当前产品结论

当前代码已经把 `/explore` 做成真实的 24 小时公开挑战 feed，不再是假数据预告。发布表单默认加入 Explore，并明确提示 Hider 可取消勾选改为私人链接；未勾选的邀请链接不会进入 feed。Explore 用房间缩略图区分四层艺术房间，Explore 发起创作必须先完成成人邮箱 OTP。当前也已具备最小公开验证防线：Hider 可从 Explore 撤回，Seeker 可用固定原因举报，首次有效举报立即把作品从 Explore 隐藏，发布/举报/提交结果分别限流。儿童 UGC 与正式扩大公开流量前的人工审核流程仍需继续检查。

推荐的权限边界：

- 所有人都可以匿名打开和游玩公开挑战。
- 匿名用户在免费 Van Gogh 房间创建的 24 小时挑战默认加入 Explore，也可以取消勾选只保留私人链接。
- 当前匿名公开只是短 TTL 验证：挑战只有固定儿童友好词库生成的两词英文房间名，没有用户输入文字、聊天、外链或长期个人主页。Painterly 账户目前只解锁 Explore 发起创作和第二至第四层艺术房间；跨设备挑战管理与更长期公开发布仍留在后续阶段。
- 在其他艺术房间创建挑战需要账户和对应 entitlement；收到链接或在公开页游玩的 Seeker 始终免费。
- 不对“注册”本身收费，不出售寻找次数、时间或更高胜率。

Monet 第一阶段已经设为“登录即可创建”，而不是立刻收费。这样一次只验证一个摩擦：用户是否愿意为第二个房间建立账户。如果同时要求注册和付款，失败时无法判断是账号、价格还是 Monet 内容的问题。注册转化成立后，再用第五个左右的艺术房间或明确的房间组合测试付费。

## Explore 页的三条内容带

### Hard to spot

- 难度来自真实行为数据，而不是创作者自行填写。
- 只有达到配置化的最小有效尝试数后，才按找到率和完成时间进入候选。
- 举报率高、样本太少或疑似不可达的挑战不进入。

### New today

- 从最近发布且通过自动检查/抽样审核的公开挑战中取少量。
- 初期不允许自由文本标题、用户名、聊天或外链；两词英文房间名只能从代码内审核词库组合，降低儿童与 UGC 审核成本。
- 同一账户和同一艺术房间设置曝光上限，避免一人占满列表。

### Pick one for me

- 从当前合格池中选择一个随机挑战。
- 不在每次请求中对整表执行 `ORDER BY RANDOM()`；使用定时生成的候选桶、随机游标或稳定哈希采样。
- 已玩过的 challenge ID 只保存在客户端小集合中，尽量减少短期重复。

## 数据生命周期

私人挑战继续保持严格 24 小时 TTL，不因 Explore 页改变。

首轮公开验证直接复用挑战的严格 24 小时 TTL，不建立长期公开副本：

- 私人挑战只存 invitation token 哈希；默认公开且未取消的挑战额外保存可列出的 `public_token`。
- 列表 API 只返回轻量元数据，不批量返回每个角色的 base64 图像。
- 玩家打开一个挑战后才读取完整 payload。
- 候选查询先限制最多 60 个仍有效挑战，再连接尝试表计算聚合，避免随历史总量扫描。
- Worker Cache API 缓存 feed 60 秒；同一边缘节点缓存命中不读 D1。缓存按数据中心分布，因此其他节点最多延迟一个 TTL 看到变化。
- 名称搜索对规范化的 `room_name_search` 做索引前缀范围查询；相同查询同样在边缘缓存 60 秒，不读取挑战 payload。
- 公开池达到真实规模前继续使用 D1；P95 payload、活跃公开挑战总量或扫描成本越过闸门后再评估 R2。

未来需要多日精选时，再增加独立状态机，而不是悄悄延长当前挑战：

```text
draft → pending_review → eligible → hidden/expired
```

## 跨平台账户边界

游戏必须拥有自己的内部 `account_id`，不能把邮箱、Discord ID、itch.io ID 或某个平台用户 ID 当作主键。

建议的数据关系：

```text
accounts
  id · created_at · status

auth_identities
  account_id · provider · provider_subject · verified_at
  UNIQUE(provider, provider_subject)

entitlements
  account_id · product_id · source_provider · status · external_reference

public_challenges
  account_id · challenge_id · status · eligible_until · moderation fields
```

- Web 已使用六位 email OTP；平台版本以后通过各自服务端验证的 identity token 接入同一内部账户。
- 关联两个身份必须分别证明控制权，不能仅凭相同邮箱自动合并。
- 平台购买先作为来源事件验证，再映射到内部 entitlement；是否允许跨平台使用由商店政策适配器决定，不在游戏核心里假设一定互通。
- 匿名 Seeker 不需要账户；当前 24 小时公开验证也不要求账户。跨设备管理、高级房间创作和未来长期公开内容才进入账户流程。

## 合规与滥用闸门

公开挑战会把当前的私人分享内容升级为公开 UGC，因此上线前至少需要：

1. **已完成**：发布频率限制、Hider 撤回能力，以及基于服务端签名匿名 session 的限流。
2. **已完成**：Seeker 举报入口、首次举报自动从 Explore 隐藏、受保护的管理员队列、恢复/确认隐藏和 30 天最小操作审计。
3. **已完成**：禁止用户输入的自由文本和外链；公开名称只允许审核过的两词英文组合。
4. 自动检查角色图像格式、大小、透明度和异常内容信号。
5. 针对儿童使用场景重新检查账户、分析标识符、公开作品和家长同意边界。
6. 公开挑战的独立保留/删除规则，不能依赖私人挑战的 24 小时说明。

### 扩大公开曝光前的硬性闸门

当前匿名 session 由服务端签名，客户端不能伪造已有 session，但用户仍可清除 cookie 获得新 session；同时，“首次有效举报立即隐藏”优先保护公开池，但也可能被虚假举报滥用。Turnstile 与管理员恢复入口降低了这两个风险，但匿名阶段仍不是账户级的强身份防线。

在购买流量、平台导流、媒体推广或其他会显著扩大 Explore 曝光的动作之前，以下三项必须全部完成：

- [x] 匿名发布、举报等高风险写操作已接入 Cloudflare Turnstile，并由 Worker 验证一次性 token、action 和 hostname；失败 token 不写入 D1。
- [x] 当前限流已改为服务端 HMAC 签名的匿名 session subject，不再信任客户端自报 ID；账户也已使用独立内部 `account_id`，平台接入时无需改游戏主键。
- [x] 已建立最小管理员处理入口：查看被隐藏挑战及固定举报原因、确认隐藏或恢复到 Explore，并保存 30 天最小操作审计。

**这三项技术闸门已经完成；扩大公开曝光仍需同时通过本节其余儿童 UGC、异常图像检查与内容合规条件。**

## 分阶段交付

1. **现在**：受控验证匿名、默认公开但可取消的 24 小时挑战池；Fresh/Surprise 立即可用，Sneaky 至少 3 次真实尝试才入选。
2. **当前公开验证闸门**：已完成 Turnstile、签名 session 限流、举报/隐藏、Hider 撤回和管理员查看/恢复入口；继续完成异常图像检查、儿童 UGC/供应商审查和内容清权。
3. **已完成**：接入 Monet 房间 manifest，验证“匿名免费房间 + 登录免费房间”。
4. **已完成基础层**：provider-neutral account/identity/session、email OTP 与 durable entitlement schema；平台 identity exchange、跨设备草稿和购买恢复仍待具体平台接入。
5. **收费验证**：账户和第二房间转化成立后，再测试一个明确的创作者房间 entitlement。

成功指标不是注册数本身，而是公开挑战开始率、完成率、举报率、公开 Seeker 转为 Hider 的比例，以及登录房间相对免费房间的创建完成率。
